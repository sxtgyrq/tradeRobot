# 故事场景与代码用途

本文档描述算法的应用场景。基础圆、路径点、联通点、采购点、收割点等底层定义，以 `requirements.md` 为准。

## 1. 圆的身份

主键：`id`，由圆的原始三元组 `(a, b, r)` 生成。

每个圆在 `Circle.bin` 中按 `a`、`b`、`r` 的顺序写入三个 `int`。每个 `int` 占 `4` 字节，因此一个圆固定占 `12` 字节。`id` 就是这 `12` 字节按小端序转换成的十六进制字符串。

`id` 是全局唯一主键，一旦生成就不能重复、不能修改。

示例一：`(0, 0, 0)` 的 `12` 字节为：

```text
00 00 00 00 00 00 00 00 00 00 00 00
```

因此 `id` 为：

```text
000000000000000000000000
```

注意：这个例子只用于说明 `12` 字节如何转换成 `id`；正式圆中 `r = 0` 不是合法圆。

示例二：`(300, 400, 500)` 的 `12` 字节为：

```text
2c 01 00 00 90 01 00 00 f4 01 00 00
```

因此 `id` 为：

```text
2c01000090010000f4010000
```

`id` 的正则表达式：

```regex
^[0-9a-f]{24}$
```

## 2. 初始状态

故事从第 `25` 根 K 线开始，也就是从 `index = 24` 开始。

K 线序号按照程序员习惯，从 `0` 开始计数：

```text
第 1 根 K 线  = index 0
第 25 根 K 线 = index 24
```

系统聪总量为 `210000000000` 聪，聪永不增发。

初始状态下，全部聪都集中在收割点；除收割点以外，其余地点都没有聪。

每个采购点初始拥有 `1000U`，以及 `0` 聪。

数据初始化时，必须先区分交易点类型。交易点只有两类：收割点和采购点。

所有交易点账户初始都拥有 `1000U`。

收割点账户初始额外拥有 `210000000000` 聪。

采购点账户初始拥有 `0` 聪。

每个交易点账户都需要包含聪余额、`U` 余额、合约单列表和现货单列表。

收割点账户的归属 ID 使用虚拟圆 `(0,0,0)`：

```text
OwnerCircleId = 000000000000000000000000
```

这个 ID 只表示收割点账户的虚拟归属，不表示一个合法真实圆。收割点实际落在哪个圆的路径点上，应使用 `PointCircleId` 和 `PointIndex` 判断。

所有总资产计算都统一折算成聪价值。`U` 资产按照对应 K 线价格折算成聪价值。

第一次分发计算系统总资产时，按照程序当前实现，使用 `allData[23].closeValue` 作为折算价格。

也就是使用第 `24` 根 K 线（`index = 23`）的收盘价，把所有交易点持有的 `1000U` 折算成聪价值后计入系统总资产。交易点包括 `1` 个收割点和所有采购点。

```text
系统聪总量 = 210000000000 聪
初始收割点余额 = 210000000000 聪
收割点初始 U 资产 = 1000U
采购点初始 U 资产 = 采购点数量 * 1000U
所有交易点初始 U 资产 = (采购点数量 + 1) * 1000U
收割点初始 U 折算聪价值 = 收割点初始 U 资产按 allData[23].closeValue 折算成聪
所有交易点初始 U 折算聪价值 = 所有交易点初始 U 资产按 allData[23].closeValue 折算成聪
初始收割点总资产 = 初始收割点余额 + 收割点初始 U 折算聪价值
系统总资产 = 系统聪总量 + 所有交易点初始 U 折算聪价值
收割点保留线 = 系统总资产 * 12%
多出的资产 = 初始收割点总资产 - 收割点保留线
```

如果 `多出的资产 <= 0`，则本次不配送。

如果 `多出的资产 > 0`，并且收割点当前可用聪足够完成本次分发，则计算配送总额。

```text
配送总额 = 多出的资产 * 20%
收割点剩余 = 初始收割点余额 - 配送总额
```

第一次分发时，`配送总额` 对所有采购点平均分配，并且实际分发资产只使用聪。

## 3. K 线主流程

当前蜡烛图必须已经具备五行属性，才进入这套流程。

每根具备五行属性的 K 线按照固定顺序推进：

```text
开盘
-> 归还收割聪（index % 24 == 0）
-> 分发（index % 24 == 0）
-> 现货交易
-> 合约交易
-> 收盘费用收取（index % 24 == 23）
-> 破产清算检查；如果发生破产清算，并且满足流动性不足条件，则给收割点注入流动性
-> 如果发生破产清算，则补圆
-> 如果补圆，则重算线路
```

24 根 K 线算一轮。

当 K 线走完最新蜡烛图后，图形保留，圆的数据不丢弃。但是行情流程要从 `index = 24` 重新开始。

重新开始时，`U` 和聪要重新分配。旧挂单和旧合约全部清空，只保留圆的数据。

## 4. 分发规则

所有分发都使用同一条规则：先看收割点总资产。

```text
收割点保留线 = 系统总资产 * 12%
多出的资产 = 收割点当前总资产 - 收割点保留线
```

如果 `多出的资产 <= 0`，则本次不分发。

分发只使用聪，不直接分发 `U`。

分发发生前，程序必须先处理上一轮待归还的收割聪。正常情况下，分发阶段开始时不应再存在待归还聪。

如果因为异常数据导致仍存在待归还聪，这部分聪视为收割点的债务，不计入可分发资产，也不能用于本次分发。

如果收割点当前可用聪不足以完成本次分发，则本次不分发，不在分发阶段临时触发现货调仓。

如果 `多出的资产 > 0`，并且收割点当前可用聪足够完成本次分发，则：

```text
本次配送金额 = 多出的资产 * 20%
每个采购点获得 = 本次配送金额 / 采购点数量
```

配送不是直接到账，而是依据路径算法执行。

每一份配送，都要从收割点出发，沿着 `收割点 -> 采购点` 的路径前进。这个过程中会经过若干路径点、联通点和圆弧。

也就是说，“平均分配”只表示每个采购点应该获得的目标金额相同；真正配送时，聪必须沿路径流动，并且会路过若干圆弧。

这些路径中路过的圆弧，可能属于做多圆，也可能属于做空圆。

当路径路过某个圆的圆弧时，这个圆会产生对应订单：

```text
路过做多圆 -> 产生做多单
路过做空圆 -> 产生做空单
```

这里的“路过一次圆”，按路径上连续同一个圆的路径点段来定义。

例如路径依次经过的圆序号为：

```text
3, 3, 3, 8, 8, 3, 3
```

则表示三次路过：先路过圆 `3` 一次，再路过圆 `8` 一次，最后再次路过圆 `3` 一次。

如果同一条路径多次路过同一个圆，不合并计算；每路过一次，就按这一次经过的圆弧单独生成一张合约单。

分发目标仍然是采购点，但产生合约单的主体不是采购点所属圆，而是路径实际路过的圆。

当路径路过圆 `circleIndex = X` 时，需要找到 `OwnerCircleIndex == X` 的圆账户，由这个圆账户产生合约单。

收割点账户使用虚拟归属圆 `(0,0,0)`，不代表真实圆，因此不参与“被路径路过圆账户”的匹配。

当 K 线的 `index % 24 == 0` 且 `index > 0` 时，先归还上一轮收割中实际收到的聪，再按统一分发规则检查收割点是否有超额资产。

归还收割聪属于 `收割点 -> 采购点` 的真实聪流动，因此归还时也要按路径产生路径效应。

因此本轮开盘处理分两步：

```text
第一步：归还上一轮收割中实际收到的聪
第二步：检查收割点总资产是否超过系统总资产的 12%；如果超过，就按统一分发规则处理
```

## 5. 挂单与撮合规则

当前 K 线新挂出的现货单和合约单，不能在当前 K 线内立即成交。

现货单和合约单至少要等到下一根 K 线，或者更后面的 K 线，才允许参与撮合。

这样可以避免同一根 K 线里不断挂单、成交、再挂单、再成交，形成无限循环。

对于已经允许参与撮合的挂单，买的、卖的只要价格落在当前 K 线的范围内，就必须在这根 K 线里完成交易。

合约撮合时，也按照当前 K 线的价格来撮合交易。这个交易类似交易所的撮合规则：多单和空单在当前 K 线的价格范围内相遇，就可以成交。

如果采购点之间没有撮合完，还有没有完成的订单，就由收割点来兜底撮合。

合约开单时，开单圆账户要先把本次保证金打给收割点账户。这里的收割点承担“交易所保证金托管账户”的角色。

因此，合约还没有成交、回购或爆仓之前，保证金不再留在开单圆账户里，而是已经进入收割点账户。

合约成交时，买卖两边的合约按成交数量消失，然后由收割点账户把应该返还的保证金和止盈收益打回对应圆账户。

如果合约没有找到采购点对手方，但合约价格落在当前 K 线范围内，则由收割点兜底回购这张合约。回购时同样按合约规则结算：合约消失，收割点把应该支付的保证金和收益打回开单圆账户。

如果合约触发爆仓，则这张合约消失，保证金留在收割点账户，不再返回开单圆账户。爆仓不是一次交易撮合，也不是收割点兜底回购，因此不产生路径效应。

如果这一根 K 线里没有挂单的合约与现货完成撮合成交，则只跳过成交结算；这根 K 线仍然要继续执行后续的收盘费用收取和破产检查。

如果这一根 K 线里发生了撮合成交，则先完成成交结算，然后继续进入后续的破产清算检查。

## 6. 现货交易

圆与圆之间会进行现货交易，现货交易采用挂单形式。

现货交易的目的，是让每个圆的资产配置靠近自己的目标比特币保留比例。

资产占比参照当前 K 线的开盘价计算。

每个圆都有自己的目标比特币保留比例。这个比例由圆的 `12` 字节数据决定：对这 `12` 字节做 `SHA256`，取哈希结果的第一个字节，把这个字节当作数字，再对 `80` 取余。

圆 ID 由 `Circle.bin` 中该圆的原始 `12` 字节数据直接转换得到：每个字节写成两位小写十六进制字符，因此圆 ID 固定为 `24` 个字符。

```text
档位 = SHA256(圆的12字节数据)[0] % 80
```

这样每个圆会落在 `0` 到 `79` 档，共 `80` 档。

```text
0 档  -> 保留 10% 的比特币
79 档 -> 保留 89% 的比特币
```

因此：

```text
目标比特币保留比例 = 10% + 档位
```

当圆当前的资产配置比例缺失，或者资产配置比例不符合自己的目标比特币保留比例时，这个圆就挂出现货单。

现货挂单的价格，从当前 K 线的价格范围内随机取值。

```text
现货挂单价 ∈ [当前 K 线最低价, 当前 K 线最高价]
```

现货交易的顺序，按照偏离目标比例的百分比进行；偏离越大的圆，越优先交易。

配对时，优先选择资金比例最不协调的圆。

也就是说，谁的聪资产或 `U` 资产偏离目标比例最严重，就优先参与现货交易。

例如，高于目标比特币保留比例最多的圆，优先去找低于目标比特币保留比例最多的圆配对。

这个配对过程一直持续，直到没有圆还需要通过资产配对来修正偏离。

如果圆与圆之间配对不成功，就和收割点进行交易。同样，现货交易里没有完成配对的，也要与收割点进行交易。

与收割点进行现货交易，也要经过路径，并且同样会产生路径效应。

收割点可以用 `U` 负数兜底买入聪，但收割点的聪不能为负数。

因此，当收割点作为现货卖方兜底时，最多只能卖出自己当前实际持有的聪；如果收割点没有可用聪，则这笔兜底卖聪交易不能成交。

现货交易经过路径时，也会产生对应的做多单或做空单：

```text
路径经过做多圆的圆弧 -> 产生做多单
路径经过做空圆的圆弧 -> 产生做空单
```

这些由路径产生的做多单或做空单，仍然形成对应的杠杆效应。

收割点也会参与现货调仓：

```text
收割点 U 资产比例超过 50%  -> 挂单买入聪
收割点聪资产比例超过 50% -> 挂单买入 U
```

这类现货交易的目的，是尽量让收割点的 `U` 资产和聪资产保持平衡。

现货交易完成后，继续交易合约。

## 7. 聪流动与路径效应总规则

路径效应由三类行为触发：

```text
聪的流转
现货交易
合约撮合
```

只要发生了聪从一个交易点账户流向另一个交易点账户，就必须按照这两个交易点之间的路径计算路径效应。

给收割点转聪，也属于聪的实际流动，因此同样会产生路径效应。

现货交易无论交易对象是采购点还是收割点，只要成交，就必须按照成交双方交易点之间的路径计算路径效应。

合约撮合包括两个合约之间的撮合，也包括收割点作为交易所对未完成合约进行兜底回购。只要形成合约撮合成交，就必须按照成交双方交易点之间的路径计算路径效应。

`U` 的流动不产生路径效应。

如果一笔业务只发生 `U` 转移，而没有发生聪转移，则这笔业务本身不触发路径效应。

如果一笔业务同时包含聪流动和 `U` 流动，则 `U` 流动本身不额外触发路径效应；路径效应仍然只计算一次。

```text
采购点 -> 收割点 转聪 -> 产生路径效应
收割点 -> 采购点 转聪 -> 产生路径效应
采购点 -> 采购点 转聪 -> 产生路径效应
聪开单合约止盈，收割点 -> 采购点 转聪 -> 产生路径效应
现货交易成交 -> 产生路径效应
两个合约撮合成交 -> 产生路径效应
收割点兜底回购合约 -> 产生路径效应
任意账户之间只转 U -> 不产生路径效应
```

## 8. 合约交易与路径效应

做多单和做空单的杠杆倍数都按 `E` 倍计算。

`E` 表示自然常数的近似值，可以取 `6` 位有效数字，当前取 `2.71828`。

做多单的止盈比例为 `46/45`。

做空单的止盈比例为 `45/46`。

每一张合约单都需要记录完整合约信息，至少包括：

```text
五行属性
做多或做空方向
开单账户类型：U 或聪
开单金额
开单价格
杠杆倍数
名义仓位
止盈价
爆仓价
创建 K 线 index
允许交易 K 线 index
路径经过的圆
路径圆弧段
```

当前爆仓价先按无维护保证金的基础公式计算：

```text
做多爆仓价 = 开单价 * (1 - 1 / E)
做空爆仓价 = 开单价 * (1 + 1 / E)
```

如果后续引入维护保证金率、补保证金或更复杂的交易所规则，再调整爆仓价公式。

所以做多单和做空单的最终结果只有两种：要么爆仓，要么止盈。

如果同一根 K 线同时触及止盈价和爆仓价，由于无法知道真实盘中先后顺序，就用这根 K 线的方向来判断先后。

做多单：

```text
收盘价 > 开盘价 -> 优先判定为先触发止盈
收盘价 < 开盘价 -> 优先判定为先触发爆仓
收盘价 = 开盘价 -> 方向不明确，保守判定为先触发爆仓
```

做空单：

```text
收盘价 < 开盘价 -> 优先判定为先触发止盈
收盘价 > 开盘价 -> 优先判定为先触发爆仓
收盘价 = 开盘价 -> 方向不明确，保守判定为先触发爆仓
```

投资比例只由本次路径在该圆上实际走过的弧度决定。

```text
弧度占比 = 本次路径走过的弧度 / 2π

正常投资比例 = 弧度占比 * 0.2
           = 本次路径走过的弧度 / 2π * 0.2
```

如果一条路径连续经过同一个圆的一段圆弧，则这一段圆弧单独计算弧度，并生成一张合约单。

如果后续路径再次回到同一个圆，则视为新的一次路过，重新按新的圆弧段计算弧度，并再生成一张合约单。

同一个圆内计算路径经过弧度时，必须按照该圆路径方向上的正向环形距离计算。

如果后一个路径点序号小于前一个路径点序号，表示这段路径穿过了圆上 `x` 最大的极点，也就是路径点 `0`，然后继续向前走；这不是负距离，也不能截断路径。

```text
若 nextPointIndex >= currentPointIndex:
    经过路径点步数 = nextPointIndex - currentPointIndex

若 nextPointIndex < currentPointIndex:
    经过路径点步数 = pathPointCount - currentPointIndex + nextPointIndex
```

每个圆都有两个账户：聪账户和 `U` 账户。

产生订单时，如果没有专门用于开单的聪或 `U`，就比较该圆的聪账户和 `U` 账户，哪个账户余额更多，就使用哪个账户开单。

比较 `U` 账户和聪账户时，必须按照当前 K 线价格折算成同一价值口径：

```text
U账户折算聪价值 = U余额 / 当前价格 * 100000000
聪账户折算聪价值 = 聪余额
```

如果 `U账户折算聪价值 > 聪账户折算聪价值`，则使用 `U` 账户开单：

```text
开单金额 = 该圆可用U余额 * 开单比例
```

否则使用聪账户开单：

```text
开单金额 = 该圆可用聪余额 * 开单比例
```

如果两个账户折算后相等，默认使用聪账户开单。

开单有可能使用聪账户，也有可能使用 `U` 账户。

如果使用聪账户开单，止盈结算后资产回到聪账户，爆仓时聪保证金留在收割点账户。

如果使用 `U` 账户开单，止盈结算后资产回到 `U` 账户，爆仓时 `U` 保证金留在收割点账户。

更准确地说，开单时保证金先从圆账户转入收割点账户托管；止盈或被收割点回购时，收割点把保证金和收益一起支付回开单圆账户；爆仓时，保证金留在收割点账户。

如果用聪作为保证金，整个过程只能在已有聪之间转移，不能因为止盈或清算凭空生成新的聪。

如果合约使用聪开单，并且最终止盈，则止盈结算时聪从收割点账户转回开单圆账户。这个过程属于 `收割点 -> 采购点` 的聪流动，因此必须产生路径效应。

聪开单合约止盈时，收割点必须有足够聪完成付款。

如果收割点聪不足，不能把收割点聪扣成负数，也不能增发聪；这属于系统资金逻辑错误，程序必须直接报错。

从交易所购买或生成合约本身，不产生新的路径效应。路径效应只在明确的交易行为里产生：

```text
两个合约互相撮合成交 -> 产生路径效应
收割点作为交易所兜底回购合约 -> 产生路径效应
合约爆仓 -> 不产生路径效应
```

## 9. 五行规则

现货单、合约单、由路径产生的做多单、做空单，都必须携带五行属性。

订单自身的五行属性，在挂单生成时确定，参照挂单生成时那根 K 线的五行属性，并且生成后固定不变。

也就是说，现货交易和合约交易产生新订单时，新订单依据生成时的 K 线产生五行属性。

交易点包括收割点和采购点。

当现货单或合约单与交易点进行交易时，交易点这一侧的五行属性按照成交发生时的当前 K 线五行属性来。

所有现货交易与合约交易，交易双方都必须进行五行比较。

五行比较结果只有三种：

```text
相克
相生
不相干
```

如果交易双方的五行属性构成相克关系，这次撮合产生的路径效应减半。

```text
相克投资比例 = 路径经过该圆的弧度 / 2π * 20% * 1/2
             = 路径经过该圆的弧度 / 2π * 10%
```

如果交易双方的五行属性构成相生关系，这次撮合产生的路径效应翻倍。

```text
相生投资比例 = 路径经过该圆的弧度 / 2π * 20% * 2
             = 路径经过该圆的弧度 / 2π * 40%
```

如果交易双方的五行属性既不相生，也不相克，则五行不相干，路径效应保持正常比例，不减半也不翻倍。

路径效应减半或翻倍，只影响这次路径产生的投资比例；不改变路径本身，不改变路径经过的弧度，也不改变成交价格。

相克关系不区分前后，只要两个五行属于相克配对，就按相克处理：

```text
金克木
木克土
土克水
水克火
火克金
```

相生关系也不区分前后，只要两个五行属于相生配对，就按相生处理：

```text
金生水
水生木
木生火
火生土
土生金
```

## 10. 收割、破产清算与补圆

当 K 线的 `index % 24 == 23` 时，在这根 K 线收盘后，收割点会向所有采购点收取费用。

每个采购点需要交出 `100` 聪。

收割方法负责收取费用和触发破产判断。若采购点实际交出了聪，则这部分聪从采购点流向收割点，属于真实聪流动，必须按路径产生路径效应。

如果采购点只用 `U` 折算支付，或者收割阶段只是取消挂单、取消合约并取回资产，则这些动作本身不产生路径效应。

在收割这 `100` 聪之前，如果采购点不能直接支付足额的 `100` 聪，就按照这根 K 线的收盘价，用 `U` 换聪。

为了保证系统聪总数不变，用 `U` 折算支付的部分只表现为 `U` 从采购点转入收割点，不会凭空生成新的聪。只有采购点实际交出的聪，才进入“待归还收割聪”账本，并在下一轮 `index % 24 == 0` 时返还。

如果用 `U` 换了以后仍然不够，并且这个采购点还有未成交的现货挂单，则先取消这些现货挂单，取回挂单里锁定的聪或 `U`，再继续支付。

如果取消现货挂单并取回锁定资产后仍然不够，就继续取消这个采购点名下未成交的合约单。

取消合约单时，取回该合约单剩余未成交名义仓位对应的剩余保证金，再继续按当前 K 线收盘价折算支付 `100` 聪。

收割阶段只取消挂单并取回锁定资产或剩余保证金，不产生新的路径效应，也不生成新的合约单。

只要最终能够足额交出 `100` 聪，这个采购点就不破产。

如果取消现货单、取消合约单并取回可用资产后仍然交不上来，这个采购点就会被破产清算。

破产清算时，破产点的残值归收割点所有。

这些残值包括：未爆仓的合约、剩余的聪、剩余的 `U`。

破产点的未完成现货单也属于残值。收割点接收后，不继续保留旧挂单。

为了保证系统聪总数永远保持 `210000000000`，破产清算阶段不能在没有真实对手方的情况下把聪凭空折算成 `U`，也不能把 `U` 凭空折算成聪。清算时只能把现货单中已经锁定的原资产归集到收割点：

```text
卖聪现货单 -> 剩余待卖聪进入收割点聪账户
买聪现货单 -> 剩余锁定 U 进入收割点 U 账户
```

破产点的未结算合约单也属于残值。由于合约保证金在开单时已经进入收割点账户托管，收割点接收破产合约后，不再重复入账这份保证金，而是直接关闭旧合约，并按当前清算 K 线判断它是否触发止盈或爆仓：

```text
当前 K 线触及止盈价 -> 合约关闭；因为收割点同时是接收方和托管方，不再额外给自己生成收益
当前 K 线未触及止盈价，或触及爆仓/止损条件 -> 合约关闭；保证金继续留在收割点账户
```

破产清算阶段的残值归集不产生新的路径效应，也不生成新的现货单或合约单。

现货撮合交易、合约撮合交易、爆仓结算、破产清算都必须满足聪守恒：

```text
所有账户可用聪
+ 未完成卖聪现货单锁定聪
= 210000000000 聪
```

注意：未结算聪保证金合约的保证金，在开单时已经进入收割点账户，所以不能在聪守恒统计里额外重复相加。

同理，计算系统总资产、收割点总资产占比、分发阈值和流动性注入阈值时，也不能把已经托管到收割点账户的合约保证金再算回开单圆账户。否则同一份保证金会在收割点余额和开单圆合约资产中重复计入。

任何代码路径只要导致上述聪总量变化，就属于程序逻辑错误，必须直接报错。

如果采购点没有破产，之前从这个采购点实际收走的聪会进入待归还账本，并在下一轮 `index % 24 == 0` 时返回。用 `U` 折算支付的部分不生成待归还聪。

一个采购点被破产清算后，要删除这个采购点账户归属的真实圆。

当前 `KChartRunWithFiveElements` 运行层不直接修改 `ConsoleMain` 的圆生成核心算法，但会通过 `KChartRunWithFiveElementsAPI` 调用 `ConsoleMain` 已提供的圆维护能力，完成物理删圆、补圆和重算线路。

也就是说，破产清算先完成账户层面的残值归集和订单移除；只要存在破产圆，就必须调用圆维护接口，把破产圆从 `Circle.bin` 中删除，补入新圆，并重新生成路线文件。

删除这个圆以后，剩余圆集合可能会从一个连通分量分裂成两个或多个连通分量。

因此补圆不能只保证新圆和任意一个旧圆相交或相切，而必须保证新圆补入以后，最终所有圆仍然属于同一个连通分量。

如果随机生成的新圆不能让整体恢复为单一连通分量，就继续生成下一个候选圆；直到补圆后满足单一连通分量约束，才能写回 `Circle.bin`。

删除旧圆并补入新圆以后，原路线文件全部失效，必须重新计算路线。

补进来的新圆，其 `a`、`b`、`r` 都是随机的，其中 `r` 可以为负数。

新增加的圆有 `10` 轮新手保护期。

一轮是 `24` 根 K 线。

在 `10` 轮新手保护期内，新圆不需要缴纳 `100` 聪。

但是分发时，新圆仍然有自己的分发份额。

新圆补进来以后，要重新计算线路。

只有发生破产清算时才补圆，只有补圆后才必须重算线路。

## 11. 流动性注入

由于收割点需要兜底，收割点的 `U` 或者聪可能不够用。

当收割点总资产小于系统总资产的 `3%` 时，我们认为系统出现流动性不足。

流动性不足时，直接给收割点增加 `U`，用来补充市场流动性。

当前规则是：按注入前的系统总资产计算，直接在收割点补充系统总资产 `12%` 的 `U`。

例如，按注入前系统总资产口径，收割点总资产占系统总资产的比例从 `2.8%`，直接增加到 `14.8%`。

这个过程只补充 `U`，聪总数维持不变，永不增发。

流动性注入发生在破产清算阶段；破产清算时，如果满足流动性不足条件，就给收割点注入 `U`。
